# PR レビュー（mekajiki スタイル）

組み込みの `/review`（浅い汎用レビュー）や `/code-review`（diff の機械的バグ/整理検出）と違い、
このskillは **設計・スコープ・規約** に踏み込んだ人手レビューを、mekajiki の型で書く。
機械的なバグ拾い・クリーンアップ検出が欲しい場面は `/code-review` に委譲してよい。

## ワークフロー

0. **セッションタイトルに PR 番号を含める**：対象が確定したら、レビューの最初の出力で `{org}/{repo}#{pr_number}`（例: `mekajiki/dotfiles#123`）を明示し、これがセッションタイトルに反映されるようにする。タイトルを直接設定するツールは無いため、冒頭で必ずこの識別子を出すことで誘導する。
1. **対象を取得**：PR番号 or URL から
   - `gh pr view <n> --json title,body,author,baseRefName,headRefName,state,additions,deletions,files,commits`
   - `gh pr diff <n>`
   - cassette / lockfile / 自動生成物・大量データは精読対象から外すが、**サイズ感は把握**して必要なら指摘する（ノイズ混入もレビュー対象）。
   - **経緯を 2 行で報告する**：mekajiki への最初の報告の冒頭に、起票者・アサインの経緯・PR 作成日・レビュー待ち日数・先行レビューの有無を書く（レビュー本文には書かない）。
   - **積み上げ PR を確認する**：同じ作者の他の open PR がこの PR の diff を含んでいないか（`gh pr list --author`）を見て、マージ順の注意を指摘に入れる。
2. **起点の issue を読む**：PR 本文の `resolve <issue URL>` から `gh issue view <n> --repo <org>/<repo>` で読む。**症状（何が困っているか）と「やること」を、レビューの間ずっと参照する**。
3. **diff だけで判断しない**：呼び出し元・呼び出し先・モデル定義を Read し、引数の意味（例: `total_price` は gross か covered か）やドメイン挙動を確認してから書く。PR 本文に書かれた説明・理由も実コードと突合する。
4. **規約と突合**：グローバル `~/.claude/CLAUDE.md` と対象リポの `CLAUDE.md` を読み、違反を具体的に引用する（例:「CLAUDE.md (Controller設計) に『…』とある」）。
5. **過去の自分のレビューに粒度を合わせる**（任意）：`gh api repos/<owner>/<repo>/pulls/<n>/comments` 等で近いPRの自分のコメントを見て、トーン・タグ運用を揃える。
6. **機械的バグ/整理は委譲可**：必要なら `/code-review` を回し、その結果を取り込みつつ、このskillでは下記「mekajiki らしさ」に集中する。
7. **分類して書く**（次節）。
8. **投稿は外向き操作**：勝手に投稿しない。レビュー本文を提示し、**「投稿して」と明示されてから** `gh pr review` / inline コメントを出す。内容の合意（「それで良い」「(a) で良い」）は投稿指示ではない。取捨選択の希望も聞く。投稿時は各コメント本文の冒頭に `🤖 < {一言まとめ}` を置き AI レビューと分かるようにする（グローバル `CLAUDE.md` の AI 発信明示ルールに従う。冗長な注釈は付けない）。`{一言まとめ}` はそのコメントの要点を一言で言い切る（例: `🤖 < ここの null チェックは握りつぶしてる`）。`🤖< AIです` のような中身の無い名乗りはしない。
   - **pending review に合流する**：投稿前に `gh api repos/<owner>/<repo>/pulls/<n>/reviews` で mekajiki の `PENDING` レビューを確認する。あれば別レビューを作らず、`POST .../reviews/<id>/events` に本文を付けて submit する。mekajiki が書いた inline コメントには `🤖` を付けない。
   - **approve は短く**：指摘が無ければ `🤖 < LGTM です。` ＋ 依頼が 1 文あればそれだけで終える（例: 「本番反映後、〇〇さんに違和感が無いか確認してみてください。」）。本文を書かない。

## 出力フォーマット

- **冒頭は `🤖 < {評価を 1 文}`**。PR がやったことを言い直さない（作者も読み手も知っている）。diffの良い点は該当する指摘の中に 1 文で添える。
- 各指摘に **タグ + 短い見出し**：
  - `[要対応]` … 規約違反・バグ・確実に直すべき問題。
  - `[要相談]` … 設計判断・スコープ・トレードオフ。断定せず選択肢（a)/(b)）を示して相談する。
  - `[nits]` … 細かい整理・ネーミング・統一。
- **各指摘は見出し 1 行 ＋ 本文 2 行まで**：根拠の引用・コードの説明は削り、判断に要る事実だけ残す。選択肢は「(a) 〜、(b) 〜」と 1 行に並べる。長くなるなら指摘を分けるか、補足を chat 側に置く。
- **抽象語で挙動を書かない**：「伝播」「連動」「重ねて」「〜を優先する」のような語は読み手が意味を聞き返す。「何を → どの順で → 結果はどれ」を、事由名・状態名・メソッド名の具体名で書く。yomiyasu はこれを検出しないので投稿前に自分で読み直す。テスト名・コメント内の語も同じ基準で見る。
- **業務判断を PR 本文に書かせるときの型**：「この PR で導入された判断として、必ず X → Y の順で〜する。以前は順序が不定だったため、Z は A か B のどちらにもなり得たが、必ず A になる。」のように、順序・以前の状態・結果を 1 段落で書くよう求める。
- **migration 行は migration がある PR だけ**：Rails等のリポで migration を含むときだけ冒頭に `migration: あり（評価）` を書く。無い PR・Rails 以外のリポでは書かない。
- **文章は通常の句読点「、。」**（全角「，．」はコミット/PRメッセージ用の別ルール。レビュー本文には適用しない）。識別子・コマンド名はバッククォートで囲む。
- 過不足ない簡潔さ。冗長な定型（## Test plan やチェックボックス）は使わない。

## mekajiki らしさ（指摘の中身）

- **issue の目的を握り続ける**：個々の指摘が issue の目的に奉仕しているかを常に問う。特に**何かを別の場所へ動かす・削る提案（テストの置き場所、責務の移動、スコープの分割）は、issue の目的を満たす検証や変更を落としやすい**。動かす提案をしたら、動かした先で issue の症状が回帰検知されるかまで確認する。
  - **issue のロードマップを確認する**。issue に書かれていることを漏らさず解決するロードマップが示されているか、敢えて対応しないことがあれば明記されているかを見る。1 PR で issue を閉じる必要はない（1 issue 対多 PR は可、1 PR 対多 issue は不可）。
  - **approve の前に、指摘を反映した状態で上記ロードマップが成り立つかを確認する**。
- **root-cause / ゼロベース**：その行を直すだけでなく「責務を分ければこのコード自体が消える」のように、症状でなく原因を指す。一つのモデル/フォーム/controller に責務を集約しすぎていないか（肥大化の兆候）を見る。
- **作り直しの提案は根拠があるときだけ**：設計の作り直し（保存先を変える、集計を事前計算にする等）は、負荷・障害・issue の未達など具体的な根拠がある場合だけ出す。既存慣習の延長なら受け入れる。ルールが未検証の段階では都度計算の方が直しやすい、のように「今の段階で何が正しいか」で判断し、早すぎる最適化を求めない。
- **実行時 altitude も見る（静的な設計の綺麗さだけで通さない）**：変更がプロセス/ホスト境界を跨いでデータや処理を受け渡すなら（リクエスト↔バックグラウンドジョブ、プロセス↔プロセス、サービス↔サービス）、各ステップが依存するリソースがその実行場所から到達可能かを追う。プロセスローカルな状態（ローカルファイル、メモリ、プロセス内キャッシュ）は共有基盤で裏打ちされない限り境界を越えない。あわせて重い/外部I/O がレイテンシ制約のある経路（リクエストサイクル、トランザクション、ロック保持区間）に居ないかを確認する。
- **migration を含む PR は必ず評価する**（書式は「出力フォーマット」の migration 行）：データ量（全行を舐めるか、ロック・実行時間）と特性（`disable_ddl_transaction!` で途中失敗したときに残る状態、deploy 中・失敗時に旧コードが新スキーマで動くか）を見る。不安があるなら、migration と backfill のリリースと、アプリケーションコードと NOT NULL 化のリリースに分けることを検討したかを問う。`strong_migrations` が通ることを安全の根拠にしない。リポ固有の注意は対象リポの CLAUDE.md に従う。
- **スコープを問う（1 PR 1トピック）**：この PR は1文で説明できるか。複数トピックの混在（機能追加＋UI変更＋リファクタ等）や、機能と無関係な infra/付随変更の同梱は、別PR/別issueへの切り出しを求める。挙動変化（例: TLS 設定の削除）が理由不明なら意図を確認する。
- **型の一意性を見る**：変数・引数は1つの型に束縛されているか。同じ引数に呼び出し経路によって異なる型を流す設計は不可。共有インターフェースへの実装追加・変更は、diff 外の既存呼び出し元の入力型まで確認する。
- **サーバが知っている値をクライアント入力で決めていないか見る**：ログイン中のユーザー（`current_*`）など、サーバ側で確定できる値をリクエストパラメータ・hidden field から受け取っていたら指摘する。署名ID・暗号化IDでも同じ（偽造できないだけで、入手されれば再利用できる）。
- **lint 抑止の追加を見る**：linter向けの除外の追加は基本的に不可。長さ系だけは無意味な細切れにするよりは許容。それ以外は妥当性を確認する。
- **規約・既存パターンに寄せる**：「コントローラーで param を加工して弾かない」「ビジネスロジックはモデルへ」等、CLAUDE.md と既存の正しいパターン（例: 既存の validation）を引いて誘導する。
- **テスト設計を見る**：private method を `send` で叩いていないか、不要な VCR カセット等のノイズを生んでいないか、副作用は `expect{}.to change{}` か、観点が網羅されているか。純粋ロジックは HTTP/VCR 抜きでテストできる単位に切り出す提案をする。
- **ネーミングを実態に合わせる**：メソッド/変数名が挙動と食い違っていたら指摘（`is_` prefix を避け述語は `?` 等）。scope・メソッド名は用途（`order_for_lock`）でなく振る舞い（何で並ぶか・何を返すか・どうロックされるか）で付ける。用途が今は一つでも他から使われ得るため。テスト名は「並行して〜」のような状況でなく、何を検証するかを書く。
- **業務判断は作者でなく mekajiki に先に聞く**：解除事由・金額・処理順序など業務判断に触れる指摘は、レビューに質問として出さない。先に mekajiki へ現状と選択肢（(a)/(b)/(c)）を示して決めてもらい、レビューには決定として mekajiki の言葉で書く（前提の当たり方はグローバル `CLAUDE.md` の「判断」節に従う）。
- **純粋なドメイン不明点は質問で出す**：業務判断でない事実確認は、勝手に正誤を断定せず、「全額0円なので※が落ちて問題ないか確認したい」のように問いとして残す。
- **リリース/ロールアウトまでが実装者の責任か見る**：feature flag や外部連携を伴う変更で、リリース時に必要な作業をリリース担当へ委譲して終わりにしていないか。実装者がロールアウト完遂まで握り、PR に残タスクが書かれているかを確認する。リポ固有のリリース運用は対象リポの CLAUDE.md に従う。

## リポ固有の規約

issue 連携の書式・リリース運用・命名規約など、リポごとの固有ルールは対象リポの `CLAUDE.md` を読んで従う（このskillには特定プロジェクト固有の情報を書かない）。
